Internals Guide

How PDF-Folio Works

PDF-Folio is a native Rust PDF reader and library manager. This guide follows data and control flow through the real system — how a page gets rendered, how the library database is organized, and how metadata and files move between devices — rather than cataloging features.

§1

Overview

One reducer, one direction of data flow.

PDF-Folio's UI (pdf-folio-ui) is built on iced, which follows the Elm architecture: a single Message enum describes every event the app can react to, a single update function is the only code allowed to change state, and everything else — clicking a page, a background render finishing, a sync pull arriving from another device — enters the app the same way, as a message.

user input / async result │ ▼ Message enum ──────────► update(&mut PDFolioApp, Message) -> Task<Message> ▲ │ │ ▼ Task<Message> ◄────────────── side effects (DB writes, rendering, network, file IO) │ ▼ view(&PDFolioApp) -> Element<Message>

Anything that might block — rendering a page through Pdfium, hashing a file, a SQLite write, a network call — runs on Tokio's blocking thread pool inside a Task, and reports back by emitting a message. Background work never mutates app state directly; it can only propose a change by producing a message, which then flows through the same reducer as a mouse click would. That single rule is what makes the rest of this document readable as a sequence of "message in, message out" steps, no matter which subsystem is involved.

State itself is grouped into nested runtime structs so call sites stay legible about which subsystem they're touching:

PDFolioApp mode: AppMode viewer: ViewerRuntime // open document, render cache, zoom, find, outline library: LibraryRuntime // entries, folders, filters, selection, drag state libraries: LibraryRegistryRuntime chrome: ChromeRuntime // menus, flyouts, confirmation modal appearance: AppearanceRuntime // theme, loaded style book settings: Settings db: Arc<Db>

The sections below go deep on three subsystems in particular — the library database, and cross-device sync — since those are where most of PDF-Folio's real complexity lives.

§2

The Rendering Pipeline

From bytes on disk to pixels on screen, one page at a time.

2.1Opening a document

pdf-folio-core::PdfDoc is a thin, UI-agnostic wrapper around pdfium-render. Opening a file only reads the page count — it deliberately does not keep Pdfium's document handle alive:

pub struct PdfDoc {
    path: PathBuf,
    page_count: u16,
}

Every later operation — render_page, text_on_page, outline, metadata_title — reopens the file through an internal with_document() helper. That's a deliberate trade: a little repeated file-open overhead in exchange for a PdfDoc that is Clone and freely shareable across async tasks, without ever holding a non-Send Pdfium handle across an .await point.

Pdfium itself is bound exactly once per process, behind a OnceLock, and every call additionally passes through a process-wide Mutex<()> guard — Pdfium's C API isn't safely reentrant across threads even when each call opens its own document. If Pdfium can't be found at all (no system library, nothing bundled next to the binary), every open/render call fails with a clear diagnostic instead of the process crashing.

The UI never calls any of this directly. It builds a Task:

// crates/pdf-folio-ui/src/viewer/tasks.rs
pub(crate) fn open_document_task(path: PathBuf) -> Task<Message> {
    Task::perform(
        async move {
            let doc = tokio::task::spawn_blocking(move || PdfDoc::open(&path)).await??;
            Ok((path, doc))
        },
        |result| match result {
            Ok((path, doc)) => Message::DocumentOpened { path, doc: Arc::new(doc) },
            Err(error)      => Message::DocumentError(error.to_string()),
        },
    )
}

spawn_blocking moves the Pdfium call off the UI thread entirely, and the resulting PdfDoc is wrapped in an Arc so later render tasks can cheaply clone a handle into their own async closures.

2.2Tiles and the render cache

render_page(index, width_px) asks Pdfium to rasterize one page at a specific target pixel width — DPI-aware, since Pdfium derives the output height from the page's own aspect ratio. The cache key reflects this directly:

pub struct TileKey { page: u16, width_px: u16 }

A page rendered at one zoom level is a different tile from the same page at another zoom level — re-rasterizing is the only way to get a crisp result, so zooming doesn't scale a bitmap in the common case, it eventually asks Pdfium for a new one. pdf-folio-core::TileCache is a thread-safe LRU (64 tiles by default) mapping TileKey -> Arc<Vec<u8>> RGBA bytes. A cache hit returns instantly without touching Pdfium; a miss triggers a background render task that reports back with a Message once the bytes are ready.

2.3Zoom without flicker

Re-rendering on every scroll-wheel tick would hammer Pdfium and stutter the UI, so zoom is split into two phases: an interim zoom, which scales the already-rendered tile on the GPU as a transform (instant, slightly soft), and a settled re-render, which fires once input goes quiet and re-rasterizes at the new width for a crisp result.

The debounce is a generation counter plus a delay task:

pub(crate) fn schedule_zoom_render(generation: u64) -> Task<Message> {
    Task::perform(
        async move {
            tokio::time::sleep(Duration::from_millis(140)).await;
            generation
        },
        Message::ZoomRenderSettled,
    )
}

Every zoom input bumps the generation counter and schedules a fresh 140 ms timer. When ZoomRenderSettled(generation) arrives, update() compares it against the app's current generation; if the user zoomed again since that timer was scheduled, the message is stale and gets dropped instead of triggering a redundant re-render. Cheap to implement, and it stops a burst of superseded renders from competing for the blocking thread pool.

2.4Text layer & outline

text_layer(index) walks Pdfium's character-level text API and returns normalized bounding boxes — fractions of page width/height, not PDF points or pixels. That normalization means the same text layer can back selection highlights and find-in-document matches at any zoom level without re-querying Pdfium; the canvas code just multiplies by whatever the current rendered page size happens to be. outline() walks Pdfium's bookmark tree into a plain OutlineNode { title, page, children } tree, independent of any Pdfium type living past the call — that's what the table-of-contents sidebar renders.

§3

The Library Database

Every named library is its own SQLite file, and every PDF's identity comes from its bytes, not its path.

pdf-folio-core::Db wraps a single bundled rusqlite connection — there's no system SQLite dependency, and no shared server. Each named library the user creates gets its own SQLite file; switching libraries in the app swaps which Arc<Db> and search index the rest of the UI talks to. This is what makes "create a second library for research papers" a cheap, isolated operation rather than a partition inside one shared database.

3.1A PDF's identity is its bytes

The single most consequential design decision in the whole database layer is this: a PDF's primary key is not its file path. It's a BLAKE3 hash of its contents.

pub fn hash_file(path: &Path) -> Result<String> {
    let mut hasher = Hasher::new();
    // ...read the file in 64KB chunks...
    Ok(hasher.finalize().to_hex().to_string())
}

pub fn import_pdf(db: &Db, path: &Path) -> Result<ImportedEntry> {
    let id = EntryId::new(hash_file(path)?);
    let inserted = db.entry_by_path(path)?.is_none();
    db.insert_entry(&NewLibraryEntry { id: id.clone(), path: path.to_path_buf(), /* .. */ })?;
    Ok(ImportedEntry { id, path: path.to_path_buf(), inserted })
}

Content-addressing a library entry pays for itself in a few different places at once, which is why it's worth pausing on rather than treating as an implementation detail:

Import is naturally idempotent

Importing the exact same file twice — even copied into two different folders, even renamed — hashes to the same EntryId. There's no separate de-duplication pass; identity is the hash.

Renames and moves don't orphan metadata

Move a PDF to a new folder on disk, or rename it, and the library entry keeps every tag, folder membership, and reading position — the row was never addressed by path in the first place.

A foundation sync can build on

A content hash is exactly what a sync system wants as a blob key: it's stable, collision-resistant, and computable independently on every device without coordination. Section 6 leans on this directly.

Extracted vs. edited metadata stay separate

Because identity doesn't depend on title/author, the schema is free to track the PDF's own metadata and the user's display overrides as genuinely different fields (below) rather than overwriting one with the other.

Folder import (import_folder) recursively scans a directory for .pdf files and imports each independently — one file failing to hash or open is recorded in an errors list without aborting the rest of the scan.

3.2Anatomy of the schema

The schema reads less like a generic document store and more like a small set of deliberate distinctions. The two that matter most: extracted metadata is never the same column as display metadata, and folder membership is app-level data that is completely separate from the filesystem.

TablePurpose
entriesOne row per PDF, keyed by its BLAKE3 id. Carries the PDF's own title/author alongside independent display_title/display_author overrides, precomputed sort_title/sort_author keys (so "The Great Gatsby" files under G), a manual_order for drag-to-reorder, and a missing flag for entries whose backing file has disappeared.
tagsA plain (entry_id, tag) join table — tags belong to entries, not to any folder.
foldersSelf-referential via parent_id for nesting. Trashing uses a trashed_at timestamp, not a boolean — see below.
entry_foldersMany-to-many membership between entries and folders, with its own manual_order for per-folder manual sort.
bookmarksPer-entry, per-page bookmark rows for local reading landmarks.
library_preferencesA generic key -> value table for sort mode, layout mode, sidebar width — UI persistence that doesn't warrant its own typed table.
import_sources, raindrop_collections, raindrop_entriesProvenance for PDFs pulled from Raindrop.io — see §3.5.
sync_* tablesThe CRDT operation log and materialized sync state — the subject of all of §6.

Foreign keys use ON DELETE CASCADE throughout — deleting a folder cascades into entry_folders and, for mirrored Raindrop collections, back into raindrop_collections — so the in-database model stays consistent without the application layer manually cleaning up joins after every delete.

3.3Folders, tags, and trash

Folders in PDF-Folio are app metadata, not filesystem directories. A PDF can live in one folder path on disk and appear in an entirely different folder structure inside the library — moving it between folders in the UI never touches the source file. That distinction is also why membership needed its own join table instead of a folder_id column on entries: it lets a future "add to multiple folders" model exist without a schema change, though today the UI treats primary placement as effectively singular per entry.

Trash — for both entries and whole folder subtrees — is soft-delete via a trashed_at timestamp rather than row deletion or a boolean flag. That single choice is what makes "restore" and "permanently delete" genuinely distinct, separately confirmed actions in the UI, rather than trash being a one-way door. It also means trashing a folder doesn't have to recursively rewrite every child row's state — the subtree's trashed-ness is a property that can be computed from parentage, and un-trashing is just clearing the timestamp back to NULL.

3.4Undo as time travel, not inverse operations

Most undo systems work by recording an inverse for every possible edit: reordering pushes a "move it back" action, tagging pushes an "untag" action, and so on. PDF-Folio does something structurally simpler: it snapshots the entire organizational state before and after an edit, and undo just restores the earlier snapshot.

/// Reversible snapshot of library organization and user-editable entry state.
pub struct LibraryOrganizationSnapshot {
    pub folders: Vec<LibraryFolderSnapshot>,
    pub entry_folders: Vec<EntryFolderMembership>,
    pub entry_trash_states: Vec<EntryTrashState>,
    pub entry_tags: Vec<EntryTagSnapshot>,
}

A bulk action — reordering, moving 40 selected PDFs into a folder, bulk-tagging, trashing a subtree — captures a LibraryOrganizationSnapshot before it runs and another after. The "before" snapshot is what undo restores; redo simply replays the "after" one. This buys a property that's easy to undervalue: every kind of organizational edit is undoable for free, including ones added later, because nothing about undo needs to know what specifically changed — it only needs to know how to fully capture and fully restore the state.

The one place this does need to know what changed is search: after restoring a snapshot, the app diffs entry trash-state between the old and new snapshot (search_changed_entry_ids) to figure out which entries need their Tantivy index entries refreshed, since undo can resurrect or re-hide a PDF that search should or shouldn't surface.

3.5Import & provenance

Not every PDF enters the library through a folder scan. The Raindrop.io integration (pdf-folio-cloud::raindrop) imports selected bookmarks, and the schema tracks where they came from: import_sources identifies the remote account/source, raindrop_collections mirrors a Raindrop collection onto a local folder (with cascading delete back to that folder), and raindrop_entries links a local entry back to its Raindrop bookmark id, remote link, and remote metadata. That provenance is what lets an import be rolled back cleanly if the user cancels partway through, rather than leaving orphaned folders and entries behind.

§4

Search & Filesystem Watching

Full-text search is indexed per page, and disk changes flow in as ordinary messages.

pdf-folio-core::SearchIndex wraps Tantivy with a small, fixed schema — and critically, indexes per page, not per document:

schema_builder.add_text_field("id",     STRING | STORED);  // entry id, not tokenized
schema_builder.add_text_field("title",  TEXT | STORED);
schema_builder.add_text_field("author", TEXT | STORED);
schema_builder.add_text_field("body",   TEXT);            // tokenized, not stored
schema_builder.add_u64_field("page",    STORED);

Each IndexDocument represents one page's extracted text, which is why a search hit carries a page number — the UI can jump straight to the matching page rather than just opening the document and leaving the user to hunt. body is tokenized for ranked matching but deliberately not stored, since page text is always cheaply re-derivable from the PDF itself through Pdfium if reindexing is ever needed.

Filesystem changes flow through pdf-folio-core::LibraryWatcher, a thin wrapper around the notify crate that filters raw OS events down to two variants:

pub enum LibraryWatchEvent {
    PdfCreated(PathBuf),
    PdfRemoved(PathBuf),
}

Only .pdf paths are surfaced, and creates/modifies collapse into the same PdfCreated variant — either way the right response is "make sure this file is imported or refreshed." Events cross an mpsc channel into an iced subscription, which turns them into ordinary Messages. The watcher itself never touches the database directly; like every other background source in the app, it only ever proposes a change.

§5

The Style System

Views describe structure and message flow; visual values live in KDL, not Rust.

Colors, radii, borders, and spacing are meant to come from pdf-folio-style rather than being hard-coded in a view function. KDL files under crates/pdf-folio-style/styles/ define themes and per-component visual states:

component "LibraryCard" {
    normal  background="#251A0E" text="#DDD0BA" border="#C8B89A1A" radius=8
    hovered background="#2E2010" border="#C8B89A2E"
}

tokens.rs turns these into typed Rust values (ThemeTokens, Spacing, FontSize) so a view writes tokens.surface instead of a raw hex string, and classes.rs/components.rs expose small styled constructors like toolbar_button(...) that accept labels and messages but never read application state themselves. In a development checkout, styles are read from disk at runtime — editing a .kdl file and reloading (View → Reload Styles, or an automatic filesystem watch) updates the running app without a rebuild, and user overrides layer in from $XDG_CONFIG_HOME/pdf-folio/styles/*.kdl on top of the bundled defaults.

§6

Cross-Device Sync

One user, several machines, and a design that keeps the server out of the way of the data.

Sync is scoped deliberately narrowly: one user's own devices, not multi-user collaboration. That narrow scope is what makes an unusually cheap architecture viable — a single self-hosted control-plane process, a serverless edge database, and pay-per-use object storage, with no fleet of application servers in between.

6.1Three tiers, one job each

Every sync operation touches up to three distinct systems, and each one exists to do exactly one thing:

Control plane — folio-sync-server

An axum service on a personal machine ("mind-palace"), reachable over Tailscale. Its only job is proving who you are and handing out short-lived credentials. It never stores or forwards library data.

Turso / libSQL — metadata

A serverless, SQL-native edge database. Holds the CRDT operation log and materialized entry/folder/tag metadata — structured, relational, transactional data.

Cloudflare R2 — blobs

S3-compatible object storage with no egress fees. Holds PDF bytes themselves, keyed by the same BLAKE3 hash used as the local EntryId.

The reason this is worth stating explicitly, rather than just as three bullet points, is that the placement of the boundary between them is the actual design decision — and it's one most sync systems get wrong in one direction or the other.

6.2The role of the server: identity, not data

It would be simpler, on paper, to skip the server entirely and have the desktop app hold long-lived Turso and R2 credentials directly. PDF-Folio doesn't do this, for reasons that matter for a system running unattended on someone's own hardware:

  • A single, revocable choke point. Every device authenticates the same way — Google OAuth with PKCE — and the server is the one place that decides whether a given Google account is allowed in at all, via an explicit allow-list (PDF_FOLIO_ALLOWED_GOOGLE_SUB / _EMAIL). Losing a laptop means revoking one session, not rotating a database credential embedded in every device you own.
  • Credentials expire on their own. The server mints a session JWT with a 30-day TTL, a Turso token scoped to that same session lifetime, and R2 presigned URLs that expire in 15 minutes and are scoped to exactly one object key (blobs/<hash>.pdf). Nothing long-lived is ever handed to a client.
  • The R2 secret key can live in exactly one place. Generating a presigned URL requires R2's secret access key. That key lives only on the server; if it lived on every desktop instead, compromising any one device would compromise write access to the whole bucket.

What the server does not do is just as important: it never proxies a SQL query or a PDF's bytes. Once the desktop app has a Turso token, it speaks Turso's HTTP (Hrana) protocol directly to Turso. Once it has a presigned R2 URL, it uploads or downloads the PDF directly to R2. The server's job ends the moment it hands back a token or URL — it is a credential broker sitting beside the data path, not inside it, which is exactly what keeps this a "zero-cost, single-user" architecture instead of one that needs to scale a proxy with usage.

Desktop App folio-sync-server Turso / R2 │ │ (mind-palace, via Tailscale) │ │ ── Google OAuth (PKCE) ────► │ │ │ │ ── verify + check allow-list ──► │ │ ◄── session JWT (30d) ────── │ │ │ │ │ │ ── GET /token/turso ───────► │ │ │ ◄── db url + auth token ──── │ │ │ │ │ ── SQL over Hrana, direct ─────────────────────────────────────►│ │ │ │ │ ── POST /token/r2/upload ──► │ │ │ ◄── presigned PUT URL (15m) │ │ │ │ │ ── PDF bytes, direct PUT to R2 ────────────────────────────────►│

6.3Why both Turso and R2 — not one or the other

It's fair to ask why this needs two remote stores instead of one. The short answer is that metadata and blobs have almost opposite storage requirements, and PDF-Folio's split lines up exactly with that difference rather than being an arbitrary choice of two vendors.

Library metadataPDF blobs
ShapeSmall, structured rows — titles, folder trees, tags, reading positionLarge, opaque binary files, sometimes tens of megabytes
Access patternFrequent, small reads/writes; needs relational queries and ordering ("everything changed since sequence N")Infrequent, whole-object transfer; content never mutates once written
Consistency needNeeds a real query engine for CRDT replay: filtering, ordering by logical time, per-entity lookupsNeeds none of that — a blob is fetched by hash or not at all
Right toolTurso/libSQL — SQL-native, edge-replicated, cheap for many small transactional operationsCloudflare R2 — S3-compatible object storage, no egress fees, priced for large binary payloads

Putting PDF bytes inside Turso would work in the narrow sense that libSQL can store blobs, but it would mean every metadata sync — even one that only renamed a folder — pulls against a database bloated with megabytes of unrelated PDF content, and it would tie blob replication to a database engine that isn't priced or built for bulk binary egress. Conversely, trying to make R2 hold the CRDT operation log would mean giving up exactly the thing a relational engine is for: querying "every operation for this library with a logical time greater than N," which the sync algorithm in §6.4 depends on directly. The two stores aren't redundant with each other; each one is doing the part of the job the other one is bad at.

One more detail worth surfacing: PDF bytes are never uploaded from an arbitrary user file path. Before a blob upload, PDF-Folio copies the source file into a managed, content-addressed local cache and relinks the library entry to that managed path. Sync always uploads from that stable cache location, keyed by the same BLAKE3 hash used as the entry's identity (§3.1) — the R2 object key is literally blobs/<hash>.pdf. That's the payoff of content-addressing showing up a second time: the same hash that made import idempotent is what makes a blob's remote name computable independently on every device, with no coordination and no naming collisions.

6.4The CRDT metadata model

Local metadata edits are captured as an append-only, per-device operation log (sync_crdt_operations), where every row is an immutable fact rather than a value that gets overwritten in place:

op_id, library_id, device_id, logical_time, entity_kind, entity_id, payload, ...

entity_kind is entry, folder, or entry_folder — plus a fourth, synthetic library kind used by a separate stream covering library existence itself (§6.4.1). Each device keeps its own monotonic logical_time counter per library. Conflicts resolve as a deterministic last-writer-wins register, computed purely from the operation log rather than from any wall-clock trust between devices:

fn operation_wins(candidate: &SyncCrdtOperation, current: &SyncCrdtOperation) -> bool {
    (candidate.logical_time, candidate.device_id.as_str(), candidate.op_id.as_str())
        > (current.logical_time,   current.device_id.as_str(),   current.op_id.as_str())
}

For a given (entity_kind, entity_id), the operation with the highest (logical_time, device_id, op_id) tuple wins. Logical time decides most conflicts; device id and op id are pure tiebreakers that guarantee every device computes the exact same winner from the exact same operation history, with zero coordination required between devices to agree. A sync pass then materializes the winning operations back into ordinary rows (sync_entries, sync_folders, sync_entry_folders) that the rest of the app actually reads from.

Because the whole model is built on durable, replayable facts rather than one shared mutable row, running a sync pass twice, out of order, or interrupting it halfway through is always safe — worst case it repeats a small amount of work, it never corrupts state.

6.4.1A second, synthetic stream: the library registry

Library existence — which named libraries exist at all, and their display names — syncs through its own independent CRDT stream, using a synthetic id (REGISTRY_LIBRARY_ID = "__pdf_folio_registry__") with entity_kind = "library". This deliberately decouples "does this library exist" from "what's inside it": a library's contents only begin syncing once the registry stream agrees the library exists on both ends, which avoids a whole class of bugs where a half-created or half-deleted library leaves orphaned metadata behind on another device.

6.5A sync pass, start to finish

Putting §6.2 through §6.4 together, here is literally what happens during one automatic sync pass:

  1. Preflight. Local changes since the last pass are snapshotted into new CRDT operations — but only where a payload actually differs, since each entity's last known payload hash is tracked to keep this idempotent. The device then checks Turso's remote operation-sequence head against its own last-seen cursor. If nothing changed locally and the remote head hasn't moved, and no blobs are waiting to upload, the pass stops here — the common case is two cheap reads, not a full round trip.
  2. Upload blobs. Any content-addressed PDF not yet confirmed present in R2 is copied into the managed cache (if needed) and uploaded via a presigned PUT URl.
  3. Push operations. This device's not-yet-pushed CRDT operations are inserted into Turso's shared log with ON CONFLICT DO NOTHING, so re-pushing after a partial failure is always safe.
  4. Pull operations. Operations appended remotely since this device's last checkpoint are fetched by sequence number.
  5. Materialize. Winners are recomputed for every touched entity and written into the local sync_* tables.
  6. Hydrate. Any newly-materialized entity this device has never seen locally gets inserted into the actual library (folders, memberships, entries), and its PDF blob is downloaded from R2 into the local cache if not already present. An existing local entry whose file went missing can be relinked to a newly-available blob here instead of being duplicated.

The desktop app runs this automatically right after Google sign-in, immediately after any local library or reading-progress edit, and on a periodic idle timer as a safety net — thanks to the preflight step, none of those triggers are expensive when there's genuinely nothing to sync.

6.6CLI entry points

Every piece of the flow above is also reachable directly from the command line, which is how the whole path gets smoke-tested against a second machine:

cargo run -p pdf-folio-main --bin pdf-folio -- sync health          # ping the control plane
cargo run -p pdf-folio-main --bin pdf-folio -- sync auth            # run the Google PKCE flow
cargo run -p pdf-folio-main --bin pdf-folio -- sync status          # show local sync state
cargo run -p pdf-folio-main --bin pdf-folio -- sync ensure-schema   # create the Turso schema
cargo run -p pdf-folio-main --bin pdf-folio -- sync sync-once       # run one full pass

sync-once is the standard second-machine smoke test: it uploads local blobs, runs the exact same CRDT pass the UI's auto-sync loop uses, and hydrates pulled blobs — exercising auth, the control plane, Turso, R2, and remote-library hydration in one shot.

§7

Life of a Bulk Action

One concrete walk-through, tying every subsystem above together.

Consider: select 40 PDFs, drag them onto a folder.

  1. Card and row clicks accumulate into LibraryRuntime's selection set (shift-click for ranges, ctrl-click to toggle) — handled synchronously in update(), no async needed for selection itself.
  2. Dropping onto a folder card resolves through the drag state machine in pdf-folio-ui::components::library, which is pure geometry and hit-testing and knows nothing about the database.
  3. update() captures a LibraryOrganizationSnapshot (§3.4), performs the entry_folders upserts on the blocking pool the same way rendering runs (§2.1), and emits a completion message when done.
  4. The write bumps updated_at on every touched entry — which is exactly what the next sync preflight (§6.5, step 1) will notice, causing those membership changes to be captured as CRDT operations on the next pass.
  5. If a filesystem watcher event or another device's sync pull arrives concurrently, both surface as ordinary messages and fold into the same single-threaded reducer — there is no separate code path for a local edit versus a remote one once it reaches the message loop.

Rendering, importing, searching, syncing, undo — every one of them is built from the same shape: background work on the blocking pool, a message describing what happened, and a single reducer that is the only thing allowed to actually change state.
